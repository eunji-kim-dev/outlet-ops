# AI 도구 사용 기록

이 프로젝트는 기획 단계부터 AI 활용을 전제로 시작했습니다. 대신 어디까지 자동화하고, 어디서부터 직접 검증하는지 명확한 기준을 세워 작업을 진행했으며, 그 기준과 실제 활용 방식을 아래와 같이 정리하였습니다.

## 도구 구분 목적

우선 **OpenAI Codex**를 통해 구현 대부분을 완성했습니다. 주요 작업 범위는 백엔드·프론트엔드 기능 개발, 테스트 코드 작성 및 실행, 오류 로그 분석, Railway·Vercel 배포 설정, 문서 초안 작성까지 포함합니다.

반면, **Claude Code**는 프론트엔드 CSS 디자인 개선에만 제한적으로 사용했습니다.

Claude Code가 디자인 작업에 강점을 보여 해당 부분만 맡겼습니다. 이때 이미 기능 개발이 완료된 상태라 레이아웃만 손보고, 기능 및 로직 구조에는 영향이 없도록 아래와 같은 조건을 명확히 제시했습니다.

- API 호출 함수, 요청 주소, 요청 본문 구조 변형 금지
- 상태 관리 로직 변경 금지
- `index.css`와 JSX의 화면 구조 및 className만 수정
- UI 라이브러리 추가 금지

작업 완료 후엔 Codex로 변경 사항 전체를 점검하면서 API 함수, 이벤트 처리 로직, React Router 경로가 그대로 유지되는지 다시 확인했고, ESLint 및 프로덕션 빌드로 최종 검증했습니다.

## 단계별 도구 활용 과정

### 백엔드 구조 설계 및 개발

Codex를 활용해 먼저 도메인 기반 패키지 구조(Controller → Service → Repository → Entity → DTO)를 설계했습니다.

매장, 상품, 재고, 판매, 발주, 매출 집계 등 전 기능을 이 구조에 따라 나눴습니다. 초반에는 코드 작성 전에 파일 분리 이유를 설명받고 직접 구조를 검토했으며, 익숙해진 이후 반복적인 구현은 Codex에 맡기고 Swagger로 직접 동작을 검증하는 방식으로 진행했습니다.

### 테스트 코드 작성

테스트 역시 Codex로 작성 후 실행했습니다. 재고가 음수로 떨어지지 않는지, 판매 시 실제 재고가 차감되는지, 재고 부족 시 판매와 재고 변경이 모두 정상적으로 롤백되는지 등을 중점적으로 확인했습니다.

발주 기능에서는 입고 처리 시 재고 증가, 이미 입고된 발주나 취소된 발주 재입고 예외 처리도 검증했습니다. 집계 기능은 날짜별 집계 및 멱등성(같은 날짜 재집계 시 중복 생성 방지), 대시보드 API 검증, 잘못된 요청값 예외 처리 등을 포함했습니다.

최종적으로 41개의 백엔드 테스트를 모두 통과했습니다.

### React 프론트엔드 구현

프론트엔드는 React를 처음 학습하면서 Codex의 설명을 바탕으로 프로젝트를 진행했습니다. JSX 구조, `export`/`import`, `useState`, `useEffect`, props, 라우팅 등 핵심 개념을 익힌 후, 재고 관리, 판매 등록, 발주 관리, 매출 대시보드 등 네 개 화면의 API 연동을 Codex로 처리했습니다. 각 화면별 구현 후 직접 브라우저에서 확인하고 개선점을 찾아 반복적으로 피드백했습니다.

### Claude Code를 활용한 디자인 개선

기능 구현이 끝난 후, 디자인 작업만 Claude Code에 의뢰했습니다. 주요 개선점은 다음과 같습니다.

- 상단 가로 메뉴를 관리 시스템에 적합한 사이드바 형태로 변경
- 입력 폼, 표, 버튼, 알림, 상태 배지 등 UI 스타일 일관성 확보
- 모바일 환경에서 표가 넘치지 않고 카드 형식으로 쌓이도록 개선
- 운영체제 환경에 맞춰 적용되는 다크 모드 추가
- 데이터 미존재 시 안내 화면 구성

### 배포 및 장애 대응

DB 정보와 API 주소를 환경 변수로 분리하고, CORS 설정, Railway용 Dockerfile, Vercel용 SPA rewrite 등을 구성했습니다. Railway CLI 배포 및 런타임 로그 분석, MySQL 변수 참조 설정도 Codex와 함께 처리했습니다. 중간에 발생한 이슈들은 별도의 [트러블슈팅](TROUBLESHOOTING.md) 문서에 정리했습니다.

## 실제 활용한 프롬프트 예시

```text
코드를 전부 작성하기 전에 파일을 왜 나누는지 설명해줘.
```

```text
재고 조회와 수량 변경 화면을 API까지 연결해줘.
```

```text
재고가 음수가 되는지, 조회가 되는지 등 통합 테스트를 전부 작성해줘.
```

```text
배포 오류 로그를 확인하고 실제 원인을 찾아줘.
```

단순히 "고쳐줘"라고만 하면 오류 메시지는 사라질 수 있지만, 근본적인 원인이 해결되지 않는 경우가 반복됐습니다. 이 때문에 배포 단계에서는 반드시 로그를 분석해 원인을 명확히 확인하도록 프로세스를 정립했습니다.

## 검증 기준

AI가 제안한 결과를 곧바로 완료 처리하지 않도록 각 단계별로 별도의 확인 절차를 마련했습니다.

- API는 Swagger를 통해 요청과 응답을 직접 점검  
- 화면은 브라우저에서 손수 조작하여 동작 확인  
- 백엔드는 JUnit과 Spring Boot 통합 테스트로 검증  
- 프론트엔드는 ESLint와 Vite 프로덕션 빌드 활용  
- 실제 MySQL을 연결한 뒤 판매, 발주, 집계 시나리오에 대한 E2E 테스트  
- 배포 후에는 Railway 로그와 함께 Health 체크, OpenAPI, CORS 응답까지 재확인

## 정리

Codex는 반복되는 코드와 테스트 작성, 그리고 오류의 원인 범위를 좁히는 과정에서 유용하게 활용했습니다. 반면, 디자인 작업은 Claude Code에서 더 효율적이었기 때문에 역할을 분리해서 맡긴 것이 결과적으로 더 효과적이었습니다. 하나의 도구로 전체 프로세스를 처리하기보다는, 각 도구의 강점을 살려 구분해서 사용하는 방식이 더 바람직하다고 판단했습니다.

기능 요구사항 설정과 기술 선택은 직접 담당했고, 각 단계마다 코드에 대해 설명을 듣고 꼼꼼히 검토했습니다. 오류 메시지만 사라지고 실제 문제가 그대로 남는 상황을 피하기 위해, 언제나 원인 확인 절차를 우선으로 진행하였고, 아래와 같은 순서로 업무를 처리했습니다.

오류 재현 → 로그 및 설정 점검 → 원인 범위 좁히기  
→ 최소 단위로 수정 → 자동 테스트 적용 → 실제 환경에서 재검증

이러한 절차를 통해 배포 안정성과 품질을 높일 수 있었습니다.
